# 金铲铲之战 — GameAuto 框架适配方案

> 基于 [golden-spatula-bot-design](../2026-05-30-golden-spatula-bot-design.md) 架构分析

## 1. 架构映射

金铲铲 Bot 的流水线架构与 GameAuto 框架天然对齐：

| 金铲铲 Bot 模块 | GameAuto 对应 | 适配方式 |
|-----------------|--------------|---------|
| `device/HDCController` | `core/capture/hdc.py` + `core/input/hdc.py` | 直接复用 |
| `vision/` (OCR+YOLO+模板匹配) | `skills/tft/perception.py` + `core/perception/pipeline.py` | 多任务并行调度 |
| `brain/` (L1规则+L2查表+L3 LLM) | `skills/tft/decision.py` | 三层决策函数 |
| `game/` (生命周期状态机) | `skills/tft/states.py` | 注册 8+ 状态 |
| `config/sets/` (赛季配置) | `skills/tft/config/` | JSON 外置 |
| `models/` (YOLO/PaddleOCR/vLLM) | `core/perception/cv/` + 本地部署 | CV 模块实现 |

## 2. 状态机设计

金铲铲需要 8 个状态，比消消乐/斗地主复杂得多：

```
LOBBY → QUEUE → LOADING → ROUND_LOOP → RESULT → POST_GAME → LOBBY
                              │
                              ├── PLANNING (备战)
                              ├── COMBAT   (战斗)
                              ├── CAROUSEL (选秀)
                              ├── AUGMENT  (海克斯)
                              └── PVE      (野怪)
```

### 状态检测器 (detector)

每个状态通过模板匹配判断（<20ms，不调 VLM）：

```python
PHASE_SIGNATURES = {

    "queue":    {"template": "queue_searching", "region": (0.3, 0.4, 0.7, 0.6)},
    "planning": {"template": "planning_timer",  "region": (0.85, 0.0, 1.0, 0.1)},

    "result":   {"template": "result_rank",     "region": (0.3, 0.1, 0.7, 0.4)},
}
```

## 3. 感知层 — 多 CV 任务并行

这是与消消乐/斗地主最大的区别：不用 VLM 做主要感知，而是 CV pipeline 并行。

```
PerceptionPipeline.run(screenshot)
├── OCR 金币/血量/等级      (PaddleOCR, <50ms)
├── OCR 回合数              (PaddleOCR, <50ms)
├── 模板匹配 商店棋子        (OpenCV, <80ms)
├── 模板匹配 棋盘棋子        (OpenCV, <100ms)
├── 模板匹配 装备图标        (OpenCV, <80ms)
└── 颜色检测 备战计时器       (HSV, <10ms)
────────────────────────────────────────
总延迟 = max(子任务) ≈ 100ms
```

### 降级策略

当 CV 置信度不足时，VLM 作为 fallback：
1. 增大 ROI，重试 OCR
2. 多次截图投票（3次取众数）
3. VLM (Qwen2.5-VL) 分析截图
4. 跳过该帧，等下一帧

## 4. 决策层 — 三层混合

### L1 规则引擎 (<1ms, 90% 决策)

```python
def decide_shop(gold, hp, level, shop_units, comp_config):
    """商店决策: 买/不买/刷新"""
    # 目标阵容核心 → 必买
    # 能升星 (已有2个同名) → 必买
    # 血量>50 → 保持50金利息
    # 血量<30 → 濒死模式，全花
    ...

def decide_economy(gold, hp, level):
    """经济决策: 升人口/刷新/存钱"""
    ...
```

### L2 查表引擎 (<100ms, 装备+站位)

```python
# 装备合成表 → JSON 外置
# 站位模板 → 阵容名 → 预设坐标
# 阵容库 → comps.json (核心/灵活棋子/装备)
```

### L3 LLM (2-5s, 每局 3-5 次)

仅在关键决策点调用：
- 阵容规划 (1-4回合)
- 海克斯三选一
- 转型决策 (血量低+来牌差)
- 异常兜底

**LLM 复用 GameAuto 的 VlmClient，温度 0.3，结构化 JSON 输出。**

## 5. 目录结构

```
skills/tft/
├── config.yaml                    # 游戏参数 (rounds 等)
├── skill.py                       # TftSkill 门面
├── states.py                      # 8 个状态的 detector + handler
├── perception.py                  # 感知门面 (组装 Pipeline)
├── perception/
│   ├── ocr.py                     # PaddleOCR 封装 (金币/血量/等级/回合)
│   ├── template_match.py          # 模板匹配 (棋子/装备/阶段检测)
│   └── yolo.py                    # YOLO 预留 (敌人检测)
├── decision.py                    # 决策门面 (路由到 L1/L2/L3)
├── decision/
│   ├── rules.py                   # L1 规则引擎 (商店/经济/升级)
│   ├── lookup.py                  # L2 查表引擎 (装备合成/站位)
│   └── llm.py                     # L3 LLM 调用 (阵容规划/海克斯/转型)
├── visualizer.py                  # 棋盘可视化 + ROI 标注
├── config/
│   ├── rois.yaml                  # 归一化 ROI 区域定义
│   ├── comps.json                 # 阵容库
│   ├── items.json                 # 装备列表
│   └── item_combinations.json     # 装备合成表
└── assets/
    ├── champion_icons/            # 棋子头像 (模板匹配用)
    └── item_icons/                # 装备图标
```

## 6. 分阶段实施

### Phase 0: CV 模块实现 (1周)
- `core/perception/cv/ocr.py` — PaddleOCR 真实实现
- `core/perception/cv/template_match.py` — OpenCV matchTemplate
- 基础 HDC 连接验证

### Phase 1: 基础游戏循环 (2周)
- 8 状态注册 + 阶段检测 (模板匹配)
- 基础 OCR (金币/血量)
- 最简规则引擎 (保持50金 + 买目标棋子)
- **里程碑: 自动完成一局**

### Phase 2: 完整视觉管线 (2周)
- 商店/棋盘/装备识别
- 装备合成系统
- 基础站位
- 阵容规划器

### Phase 3: LLM 接入 + 优化 (2周)
- L3 LLM 决策 (阵容规划/海克斯)
- 经济策略调优
- scrcpy 推流降延迟
- **里程碑: 稳定前 4**

## 7. 与消消乐/斗地主的对比

| 维度 | 消消乐 | 斗地主 | 金铲铲 |
|------|--------|--------|--------|
| 状态数 | 1 | 2 | 8+ |
| 感知方式 | VLM | VLM | CV Pipeline (OCR+模板) + VLM fallback |
| 决策层 | 规则 | 规则 | L1规则 + L2查表 + L3 LLM |
| 延迟要求 | 不限 | 不限 | <300ms/帧 |
| 可视化 | 棋盘+swipe | 按钮+手牌 | ROI+棋子+装备+操作箭头 |
| 赛季更新 | 不需要 | 不需要 | 替换 JSON+图标 |
| 核心复杂度 | 求解器 | 牌型识别 | 多CV并行+三层决策 |

## 8. 关键风险

| 风险 | 缓解 |
|------|------|
| 模板匹配准确率不足 | 多尺度匹配 + 投票 + VLM 兜底 |
| CV pipeline 延迟超标 | 并行调度 + GPU 加速 (DirectML/CUDA) |
| 赛季 UI 变化 | ROI 外置配置 + 校准工具 |
| 反作弊检测 | 操作随机延迟 + 避免高频 |
