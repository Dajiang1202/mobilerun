# 手机游戏自动化 — 项目进展与难点分析

> 2026-06-04 | GameAuto Framework

---

## 1. 手机游戏自动化 vs 手机应用 GUI 自动化测试

两者的核心区别源于**是否能拿到结构化信息**。

| 维度 | GUI 自动化测试 | 游戏自动化 |
|------|--------------|-----------|
| **UI 树** | 可通过 AccessibilityService / UIAutomator 获取结构化控件树，知道每个按钮的 text、bounds、clickable 等 | 游戏使用自研引擎（Unity/Cocos/Unreal）渲染，无控件树可查，所有识别只能靠视觉 |
| **确定性** | 同一步操作的结果高度确定（点"设置"一定到设置页） | 游戏有随机性：来牌随机、对手行为随机、掉落随机、网络延迟导致帧不一致 |
| **实时性** | 不敏感，等页面稳定再操作即可 | 金铲铲备战 30 秒内必须完成操作；MOBA 需要秒级反应；射击游戏需要 <100ms 延迟 |
| **状态空间** | 有限（N 个页面，M 个弹窗） | 无限或接近无限（棋盘的每种排列、对手的每种走法、每回合的随机事件） |
| **可复现性** | 可以暂停、回退、重复 | 实时对战无法暂停，单局无法复现，调试只能靠录制回灌 |
| **反馈周期** | 即时（点按钮 → 页面跳转） | 延迟反馈（出牌 → 等出牌结果；升级 → 等几回合后看效果） |

**核心结论**：GUI 自动化的核心技术是**控件定位 + 页面导航**，游戏自动化的核心技术是**视觉感知 + 状态机 + 策略决策**。

## 2. 各游戏类型的核心难点

### 2.1 消消乐 (Match-3)

| 难点 | 说明 | 当前方案 |
|------|------|---------|
| 棋盘识别 | VLM 必须正确识别 7x7~10x9 棋盘、每种棋子的颜色/形状 | VLM + jinja2 提示词，低温度(0.2)，不深度思考 |
| 列数误判 | VLM 容易把 9 列识别成 10 列 | 后处理验证 + 宽高比校验 + 末列去重 |
| 多步求解 | 单步操作效率低，多步操作互不干扰 | `solve_board_multi()` 贪心选择独立 swap |
| 实时性 | 不敏感（回合制），800ms 截图 + 3s VLM 可接受 | 已解决 |

**难度：★★☆☆☆** — 首个适配游戏，已完整跑通。

### 2.2 斗地主 (Dou Di Zhu)

| 难点 | 说明 | 当前方案 |
|------|------|---------|
| 按钮状态识别 | 提示按钮蓝色(可用)/灰色(不可用)的区分 | prompt 强化 enabled 判断 + 代码兜底 |
| 花色点数识别 | 需要识别每张牌的具体值才能构造合法牌型 | 已要求 VLM 输出 suit+value |
| 牌型合法性 | 随机选牌可能不合规（上家出对子，你点单张） | 当前：提示 enabled→跟牌，disabled→盲出对子或单张 |
| 上家出牌追踪 | 需要知道上家出了什么牌 | last_played 字段 |
| 死胡同 | 不合规牌型点出牌无反应 | 待解决：需更智能的牌型匹配 |

**难度：★★★☆☆** — 基本流程跑通，策略仍需迭代。

### 2.3 金铲铲 (TFT)

| 难点 | 说明 | 影响 |
|------|------|------|
| **实时性** | 备战阶段 30 秒内完成买人/升星/装备/站位所有操作 | 必须 <300ms/帧感知 |
| **多 CV 并行** | 需同时 OCR 金币+模板匹配棋子+YOLO 敌人+颜色检测阶段 | 单帧总延迟 = max(子任务)，非 sum |
| **三层决策** | 90% 规则(<1ms) + 9% 查表(<100ms) + 1% LLM(2-5s) | 复杂工程 |
| **赛季更新** | 每赛季棋子/装备/羁绊/UI 全部变化 | 需配置驱动 + 快速迁移工具 |
| **算力要求** | 需要本地 PaddleOCR + YOLOv8 + vLLM(Qwen-14B) | ~22GB 显存 |
| **截屏延迟** | 鸿蒙 HDC 截屏 ~800ms，不够 | 需要 native 推流（agent.so/ArkTS APP） |
| **反作弊** | 腾讯 ACE 反作弊对输入注入敏感 | 需随机延迟 + 人类操作模拟 |

**难度：★★★★★** — 所有层面都有挑战。

### 2.4 王者荣耀 (MOBA)

| 难点 | 说明 |
|------|------|
| **实时性** | 秒级反应：团战识别、技能释放时机、走位 |
| **小地图理解** | 需要实时解析小地图 → 全图态势感知 |
| **英雄/技能识别** | 100+ 英雄，每个英雄 3-4 个技能，组合复杂度极高 |
| **3D 场景理解** | 需要理解视野、距离、兵线、塔、野怪等 3D 空间信息 |
| **策略复杂度** | 宏观（gank/推塔/打龙）到微观（走位/技能连招/U 形走位） |
| **反作弊** | MOBA 反作弊极度严格 |

**难度：★★★★★** — 最困难的游戏类型之一。

### 2.5 和平精英 (FPS)

| 难点 | 说明 |
|------|------|
| **极致实时性** | <100ms 端到端延迟（截屏+识别+决策+操作） |
| **3D 环境理解** | 需要深度估计、敌人检测、掩体识别、物资定位 |
| **精确操控** | 压枪、跟枪、瞄准需要亚像素级鼠标/触控精度 |
| **音频感知** | 需要听脚步、枪声方向 |
| **反作弊** | FPS 反作弊零容忍，任何自动化都极高风险 |

**难度：★★★★★** — 不仅是技术挑战，反作弊风险极高。

## 3. 当前进展与技术演进

### 3.1 已完成的成果

**GameAuto Framework (M1)** — 28 个源文件：
- `core/` — capture(HdcCapture) / perception(VlmClient+Pipeline) / input(HdcInput) / orchestration(StateMachine+GameLoop) / recorder(DataRecorder+ReplaySimulator)
- `skills/match3/` — VLM 棋盘识别 + 贪心求解器(solve_board_multi) + 棋盘/swipe 可视化
- `skills/doudizhu/` — VLM 两阶段识别(bidding/playing) + 按钮/card 检测 + 规则决策
- `tools/` — test_capture / test_perception / test_vlm / debug_viewer
- 配置体系：三层分离 (全局/技能默认/用户覆盖)

**消消乐** — 完整可用，支持 1 步/2 步独立交换
**斗地主** — 基本可用，策略需继续迭代

### 3.2 尝试过的技术路径与取舍

| 尝试 | 结论 | 原因 |
|------|------|------|
| **VLM 强制深度思考** | ❌ 放弃 | 延迟 10-30s，棋盘识别不需要深度推理 |
| **VLM + LLM 二次推理** | ❌ 放弃 | VLM 感知 → LLM 决策的双模型方案延迟翻倍，消消乐/斗地主不需要 |
| **纯 CV 方案(模板匹配)** | ⏳ 接口预留 | 需要大量模板制作，M2 再实施 |
| **HDC 持久化 Shell** | ✅ 采用 | 省 ~30ms，无副作用 |
| **HDC Pipe 截屏** | ❌ 不生效 | snapshot_display 不支持 pipe 输出 |
| **Daemon 流式截屏** | ⏳ 待实施 | 原理通了，缺 agent.so |

**为什么当前方案是 VLM 直出 + 规则决策？**

1. **开发效率**：VLM 改 prompt 即可适配新游戏，CV 需要标注训练数据
2. **灵活性**：同一模型可以做感知+理解，不需要为每个游戏训练专用检测器
3. **迭代速度**：消消乐一个 jinja2 文件就能跑，斗地主多两个文件就能跑
4. **适用场景**：对消消乐/斗地主这类非实时游戏，3-5s 的 VLM 延迟完全可接受

## 4. 模型选型：闭源 vs 开源

### 4.1 当前为什么用闭源模型

| 因素 | 闭源 (GPT-4o / Qwen3-VL via API) | 开源本地部署 |
|------|------|------------|
| **部署成本** | 零（API 调用） | 8×H20 GPU 集群 |
| **推理速度** | 2-5s（共享集群） | 取决于显存/量化 |
| **识别质量** | 目前最高 | FP8/INT4 量化有精度损失 |
| **迭代速度** | 改 prompt 即可 | 换模型需重新部署、调参 |

当前阶段的首要目标是**验证框架可行性 + 快速迭代游戏逻辑**，闭源 API 是最优选择。

### 4.2 切换到开源量化模型的风险

| 风险 | 说明 |
|------|------|
| **精度损失** | FP8/INT4 量化后，小元素识别（按钮状态、花色）准确率可能下降 10-20% |
| **部署运维成本** | 需要专人维护 GPU 集群、模型更新、负载均衡 |
| **推理速度** | 8×H20 部署 DeepSeek-V3-FP8，单次推理 ~1-3s，但并发受限 |
| **功能缺失** | 部分开源模型的 vision 能力不如 GPT-4o |
| **安全合规** | 内网部署需要解决模型下载、更新、安全审计 |

**建议**：短期继续用闭源 API 迭代，中长期可在算力到位后做对比测试，保留随时切换的能力。

## 5. 后续游戏扩展路线

### 5.1 游戏分类与适配策略

| 类别 | 代表 | 感知方式 | 决策方式 | 实时性要求 | 适配难度 |
|------|------|---------|---------|----------|---------|
| **休闲回合制** | 消消乐、连连看、泡泡龙 | VLM 局部截图 | 规则求解器 | 低 | ★★☆ |
| **棋牌类** | 斗地主、象棋、麻将、炉石 | VLM 全屏 + OCR 数值 | 规则 + 查表 + LLM | 低 | ★★★ |
| **自走棋/策略** | 金铲铲、多多自走棋 | CV Pipeline(OCR+模板+YOLO) + VLM fallback | L1规则+L2查表+L3 LLM | 中（30s 备战） | ★★★★★ |
| **MOBA** | 王者荣耀 | YOLO 小地图 + 英雄检测 + VLM 战略 | 宏观LLM + 微观规则 | 高（秒级反应） | ★★★★★ |
| **FPS** | 和平精英、三角洲 | 实时目标检测 + 音频 | RL 强化学习 + 规则 | 极高（<100ms） | ★★★★★ |

### 5.2 适配模式

**模式 A — Prompt 适配**（消消乐/斗地主模式）
- 改 VLM prompt 即可
- 规则决策器 <200 行 Python
- 人均 1-2 周

**模式 B — 混合感知**（金铲铲模式）
- CV Pipeline + VLM fallback
- 三层决策引擎
- 赛季配置系统
- 人均 4-8 周

**模式 C — 深度定制**（MOBA/FPS）
- 大量训练数据
- 强化学习 / 行为克隆
- 实时推流截屏
- 人均 8-16 周

### 5.4 棋牌类统一抽象

斗地主、象棋、麻将、炉石可以抽象为一个**棋牌框架**：

```
CardGameSkill (共享基类)
├── perception: VLM 识别牌面/棋盘 → 结构化 JSON
├── decision:
│   ├── L1: 牌型解析器（识别单张/对子/顺子/炸弹）
│   ├── L2: 出牌合法性校验
│   └── L3: 策略（规则/LLM）
├── opponent_tracking: 上家出牌追踪
└── visualization: 牌面+按钮标注
```

斗地主完成后，象棋/麻将/德州扑克共享 80% 代码，主要是改 prompt 和规则引擎。

## 6. 关键待解决问题

1. **截屏延迟** — 鸿蒙 HDC ~800ms，急需 native 推流（agent.so 待获取）
2. **斗地主牌型合法性** — 当前随机出牌可能不合规
3. **VLM 坐标精度** — 按钮/卡牌坐标偶尔偏移
4. **金铲铲 CV Pipeline** — M2 需要实现 OCR + 模板匹配 + YOLO
5. **开源模型评估** — 需在自有集群上做 VLM 精度对比测试
6. **多人协作开发规范** — 需要统一的 Skill 开发模板 + CI
